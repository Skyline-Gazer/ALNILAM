## Branch-protection behavior smoke

On a disposable target branch protected with the same Plan B rule values as current `dev`, CNB PR #6 demonstrated:

- With **zero statuses**, CNB reported `blocked_on=unblocked` and `mergeable_state=mergeable`; `check-status` returned success with no status entries. The branch rule does not require a check to exist.
- With an intentionally failing status (`cnb-if2-1k61pq4p0`), the PR became `blocked_on=status_check` and a merge attempt returned HTTP 409.
- A direct push to the protected scratch target was rejected by CNB.

This is a **FAIL** for strict Required Checks: the API exposes no named required-check context and says checks gate merges only if statuses exist. The actual zero-status behavior was exercised on a disposable protected PR, not inferred from UI text. A pending-but-not-finished status was not separately tested. Official [CNB trigger documentation](https://docs.cnb.cool/zh/build/trigger-rule.html) describes the conditional behavior. Direct push was rejected on the scratch protected branch; no protected `dev` or `main` write/merge was attempted. Scratch rule `97162af2214c8d27a996700157d1a327b9d41c05` was deleted, PR #6 was closed unmerged, and both scratch refs were removed.
